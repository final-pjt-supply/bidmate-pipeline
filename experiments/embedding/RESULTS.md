# 임베딩 실험 결과 (BGE-M3 / Cloudflare Workers AI / OpenSearch knn)

## 1. 배경 / 목표

GPU 없이 스케일투제로가 가능한 방식으로 BGE-M3 임베딩을 실시간 파이프라인에
편입하기 위한 사전 검증. 로컬에서 전체 파이프라인(청킹 → 임베딩 → 인덱싱 →
검색)을 한 번 완주해서 각 단계가 실제로 맞물리는지, 검색 결과가 의미 있게
나오는지 확인한다.

## 2. 구성

| 단계 | 방식 |
|---|---|
| 데이터 | bidmate `extracted/daily/` 실데이터 68개 문서 |
| 청킹 | `embedding/chunker.py` (기존 로직 그대로 재사용, 변경 없음) — 2,624개 청크, truncated 319건 |
| 임베딩 | Cloudflare Workers AI `@cf/baai/bge-m3`, OpenAI 호환 `/v1/embeddings` API (`embedding/cloudflare_embedder.py`) |
| 벡터 저장소 | 로컬 OpenSearch(docker-compose, `db/docker-compose.yml`), `knn_vector` 필드(1024차원, HNSW, cosine similarity, Lucene 엔진) |

## 3. 임베딩 실행 결과

- 2,624개 청크 전체 임베딩: **121.8초, 청크당 46ms**
- 벡터 차원 1024, 전 청크 일관됨
- 비용: Cloudflare 공식 단가 $0.012/1M 입력 토큰 기준 코퍼스 전체(약 80만 토큰) **1센트 미만**

## 4. OpenSearch 적재

- 2,624건 전체 성공, 실패 0건
- 인덱스명: `embedding-experiment-chunks`

상대적 격차가 판별 신호로 유효함(스코어 임계값 하나로 자동 필터링하려면
추가 튜닝 필요).

## 6. 검색 테스트 — BM25 (텍스트 매치) 비교

5-1 쿼리를 knn 대신 `text` 필드 BM25(`match`) 쿼리로 재실행. 목적: 정답
문서(R26BK01624671_000)가 BM25로는 상위에 뜨는지 확인해 하이브리드 검색
도입 근거를 만드는 것.

**결과: BM25로도 R26BK01624671_000이 top-5에 뜨지 않았고, "eLoran" 단독
검색도 인덱스 전체에서 매치 0건이었다.**

### 원인 분석

BM25가 못 찾은 게 아니라, **"eLoran"이라는 단어 자체가 인덱스에 존재하지
않았다.** 원본 문서(`R26BK01624671_000_doc01`)를 직접 확인한 결과, 원인이
두 단계로 겹쳐 있었다.

**근본 원인 — 추출 단계의 표 태그 경계 오인식(`parsing/` 소관)**

원문에서 `[표]`/`[/표]` 개수는 정확히 2쌍이지만, 첫 `[표]`(위치 1)와 그에
대응하는 `[/표]`(위치 7093) 사이에 **서로 다른 4개 문서 섹션**(청렴계약서약
안내문 / "1. 입찰개요"(사업명="eLoran 수신기 보정지도 지원 시스템 구축" 포함)
/ "2. 입찰일시 및 장소" / "3. 입찰참가자격" / "3-1. 제출서류")이 **하나의
표 블록으로 뭉쳐 있었다**(총 7,096자). SAMS 앰프 스펙표처럼 같은 종류의
행이 반복되는 진짜 데이터 테이블이 아니라, 원본 PDF/HWP에서 해당 페이지가
테두리 있는 폼 레이아웃으로 렌더링돼 있어 추출기가 페이지 전체(또는 그
상당 부분)를 표 하나로 잘못 인식한 것으로 추정된다. 이건 청킹(`chunker.py`)
소관이 아니라 `parsing/`의 텍스트 추출 로직 소관 — **수정 시 현재 운영 중인
추출 Lambda(pdf/hwp/hwpx)에 미치는 영향 범위를 먼저 확인해야 한다.**

**증상 악화 — 청킹의 표 절단 로직**

경계 오인식으로 생긴 7,096자짜리 블록을, 청킹 로직(기존에 merge된 표 잘림
처리: 768자 초과 시 완전 행 단위 절단, 앞부분만 유지)이 **691자만 남기고
절단**했다. "eLoran"이 있던 위치(1,445)는 절단선 밖이라 **살아남은 청크에
"eLoran"이라는 문자열 자체가 없다.** 즉 근본 원인(경계 오인식)이 만든 거대
블록을, 앞부분만 남기는 절단 전략이 핵심 식별 정보(사업명)까지 함께
날려버려 증상을 악화시켰다.

청크 데이터에 없는 정보는 BM25든 knn이든 원천적으로 못 찾으므로, 이번
케이스는 BM25 vs knn의 성능 차이가 아니다.

### 대응 방향

- **단기 완화책(청킹, 추출 수정 없이 가능)**: 표 절단을 "앞부분만 남기고
  버림"에서 "768자 단위로 순차 분할(여러 청크로 나눠 전량 보존)"로 바꾼다.
  근본 원인(경계 오인식)은 그대로 남지만, 최소한 정보 손실 자체는 막을 수
  있다.
- **근본 해결책(추출, 별도 작업으로)**: `parsing/`의 표 경계 인식 로직을
  개선해 이런 다중 섹션 뭉침을 방지한다. 운영 중인 추출 Lambda(pdf/hwp/hwpx)
  영향 범위 확인이 선행돼야 하는 별도 이슈.

### 미해결 질문

전체 2,624개 청크 중 truncated 319건(약 12%) 안에서, 이번 사례처럼 **표
태그 경계 오인식으로 여러 섹션이 뭉친 "가짜 대형 표"**가 몇 건이고, SAMS
앰프 스펙표처럼 **정말로 행이 많은 데이터 테이블**이 몇 건인지 아직 구분하지
않았다. 이 비율에 따라 단기 완화책(분할)만으로 충분한지, 근본 해결(추출기
수정)의 우선순위를 얼마나 높여야 하는지가 달라진다 — 다음 단계에서 확인 필요.

## 7. 종합

- 임베딩(Cloudflare BGE-M3) → OpenSearch knn 인덱싱 → 검색까지 파이프라인
  자체는 정상 동작 확인(2,624건 전체 성공, 무관 질문에 스코어 유의미하게
  하락)
- 하이브리드 검색(BM25+knn) 도입은 여전히 유효한 개선 방향이지만, 이번
  테스트로는 근거를 직접 확인하지 못했다(정답 문서가 절단으로 아예 빠져
  있었기 때문) — 아래 데이터 손실 문제를 먼저 손본 뒤 재검증이 필요하다.
- 더 시급한 발견은 검색 알고리즘이 아니라 **데이터 손실**이다 — 추출 단계의
  표 경계 오인식(근본 원인, `parsing/` 소관)과 청킹의 절단 전략(증상 악화)이
  겹쳐 문서 식별 정보가 통째로 유실되는 실제 사례를 하나 구체적으로 찾아냈다.

## 8. 청킹 수정 후 재검증

6절에서 발견한 "증상 악화" 요인(표 절단 시 앞부분만 유지)을 단기 완화책대로
수정했다: `embedding/chunker.py`의 표/박스 절단 로직을 제거하고, 한도(768자)
초과 시 행 단위로 여러 청크에 순차 분할(전량 보존, 오버랩 없음)하도록
변경했다. 근본 원인(추출 단계 표 태그 경계 오인식, `parsing/` 소관)은 이번
수정 범위 밖으로 남아있다.

### 8-4. knn 3종 쿼리 재실행(v1 vs v2 비교)

**5-1. "eLoran 수신기 보정지도 지원 시스템 구축 공고의 입찰 참가자격은?"**

| 순위 | v1 score / bid_id | v2 score / bid_id |
|---|---|---|
| 1 | 0.7828 / R26BK01620506_001 | 0.7790 / R26BK01623742_000 |
| 2 | 0.7783 / R26BK01624656_000 | 0.7771 / R26BK01624763_000 |
| 3 | 0.7758 / R26BK01623284_000 | 0.7735 / R26BK01623282_000 |
| 4 | 0.7732 / R26BK01623172_000 | 0.7732 / R26BK01623760_000 |
| 5 | 0.7732 / R26BK01623760_000 | 0.7731 / R26BK01623172_000 |

**정답 문서(R26BK01624671_000)는 v2에서도 knn top-5에 없다** — "eLoran"
텍스트가 이제 코퍼스에 존재함에도 knn이 여전히 못 찾는다. 이건 **하이브리드
검색이 필요하다는 걸 이번에 처음으로 직접 확인한 것**이다(6절 시점엔 정답
문서 자체가 절단으로 빠져 있어 근거를 못 만들었었다) — BM25는 정답을 1위로
정확히 찾았는데(8-3), knn은 의미적으로 "입찰참가자격" 근방인 다른 문서들만
비슷한 스코어로 나열한다. 정확한 고유명사/식별자 검색은 BM25가, 의미
기반 탐색은 knn이 맡는 하이브리드 조합이 실제로 상호보완적임을 확인.

**5-2. "소프트웨어 개발 용역 공고"** — v1과 v2 모두 "기술용역"/"소프트웨어"
계열 문서가 상위권(score 0.77~0.79대), 순위 구성원은 청크 분할 방식이 달라져
일부 바뀌었으나(예: R26BK01623284_000 표 청크가 1위로 새로 등장) 전반적
경향은 동일하게 유지됨.

**5-3. "김치찌개 만드는 법"** — v1(0.6821~0.6716) 대비 v2(0.6939~0.6744)로
절대 스코어가 근소하게 상승했으나(청크 분할로 표 청크의 개별 텍스트가 더
짧고 특정 소재(수지 시공/절단 가공 등)에 집중되며 우연히 소폭 상승한 것으로
추정), 여전히 5-1/5-2(0.77~0.79대) 대비 **약 0.08~0.10 낮은 구간**을
유지 — 무관한 질문을 낮은 유사도로 구분하는 패턴은 청킹 변경 후에도 그대로
성립한다.

## 9. 종합(갱신)

- 청킹 수정(표 절단 → 분할)으로 데이터 손실 문제는 해결 확인(truncated
