# 임베딩 실험 결과 (BGE-M3 / Cloudflare Workers AI / OpenSearch knn)

## 1. 배경 / 목표

GPU 없이 스케일투제로가 가능한 방식으로 BGE-M3 임베딩을 실시간 파이프라인에
편입하기 위한 사전 검증. 로컬에서 전체 파이프라인(청킹 → 임베딩 → 인덱싱 →
검색)을 한 번 완주해서 각 단계가 실제로 맞물리는지, 검색 결과가 의미 있게
나오는지 확인한다.

## 2. 구성

| 단계 | 방식 |
|---|---|
| 데이터 | bidmate `extracted/daily/` 실데이터 68개 문서 |
| 청킹 | `embedding/chunker.py` (기존 로직 그대로 재사용, 변경 없음) — 2,624개 청크, truncated 319건 |
| 임베딩 | Cloudflare Workers AI `@cf/baai/bge-m3`, OpenAI 호환 `/v1/embeddings` API (`embedding/cloudflare_embedder.py`) |
| 벡터 저장소 | 로컬 OpenSearch(docker-compose, `db/docker-compose.yml`), `knn_vector` 필드(1024차원, HNSW, cosine similarity, Lucene 엔진) |

## 3. 임베딩 실행 결과

- 2,624개 청크 전체 임베딩: **121.8초, 청크당 46ms**
- 벡터 차원 1024, 전 청크 일관됨
- 비용: Cloudflare 공식 단가 $0.012/1M 입력 토큰 기준 코퍼스 전체(약 80만 토큰) **1센트 미만**

## 4. OpenSearch 적재

- 2,624건 전체 성공, 실패 0건
- 인덱스명: `embedding-experiment-chunks`

## 5. 검색 테스트 — knn (벡터 유사도)

3종 쿼리로 top-5 스코어/내용 확인 (`experiments/embedding/query_test.py`).

### 5-1. 코퍼스에 확실히 있는 내용
쿼리: `"eLoran 수신기 보정지도 지원 시스템 구축 공고의 입찰 참가자격은 무엇인가?"`

| 순위 | score | bid_id | 내용 |
|---|---|---|---|
| 1 | 0.7828 | R26BK01620506_001 | 공고서 표(수요기관/계약방법/낙찰자...) |
| 2 | 0.7783 | R26BK01624656_000 | 공고서 표(수요기관/품명...) |
| 3 | 0.7758 | R26BK01623284_000 | "3. 입찰참가자격" 섹션 헤더 |
| 4 | 0.7732 | R26BK01623172_000 | 입찰 설명서 안내문 |
| 5 | 0.7732 | R26BK01623760_000 | "입찰참가자격 등록" 관련 안내 |

정답 문서(R26BK01624671_000) 자체는 top-5에 없었으나, "입찰참가자격" 관련
내용을 가진 다른 문서들이 상위권에 잡혀 의미적 관련성은 확인됨. 정답 문서가
안 뜬 이유는 6절 참고(임베딩/검색 결함이 아니라 청킹 단계의 데이터 손실).

### 5-2. 일반 탐색형
쿼리: `"소프트웨어 개발 용역 공고"`

| 순위 | score | bid_id | 내용 |
|---|---|---|---|
| 1 | 0.7765 | R26BK01620445_000 | "기술용역 입찰설명서" |
| 2 | 0.7738 | R26BK01620154_000 | "기술용역 입찰공고" |
| 3 | 0.7721 | R26BK01620050_000 | "기술용역 입찰설명서" |
| 4 | 0.7707 | R26BK01622081_000 | "1. 입찰개요" |
| 5 | 0.7704 | R26BK01620154_000 | "용역명: 아산 풍기역지구..." |

"기술용역" 계열 문서가 상위권을 채워 탐색형 쿼리로 잘 작동.

### 5-3. 코퍼스에 없을 법한 엉뚱한 질문
쿼리: `"김치찌개 만드는 법"`

| 순위 | score | bid_id | 내용 |
|---|---|---|---|
| 1 | 0.6821 | R26BK01624022_000 | 창호 절단 규격 표 |
| 2 | 0.6771 | R26BK01623782_000 | 이미지 참조 나열 |
| 3 | 0.6735 | R26BK01624022_000 | 창호 배수구 가공 |
| 4 | 0.6728 | R26BK01624063_000 | 이미지 참조 나열 |
| 5 | 0.6716 | R26BK01624022_000 | 창호 유리고정테/잠금장치 |

**스코어가 1/2번(0.77~0.78대) 대비 3번(0.66~0.68대)에서 약 0.10 하락** —
knn 검색이 무관한 질문을 유의미하게 낮은 유사도로 구분함을 확인. 다만
완전 무관한 질문도 절대 스코어가 0.68까지 나오는 건 cosine similarity의
baseline이 BGE-M3 임베딩 공간에서 원래 높게 깔리기 때문 — 절대값보다
상대적 격차가 판별 신호로 유효함(스코어 임계값 하나로 자동 필터링하려면
추가 튜닝 필요).

## 6. 검색 테스트 — BM25 (텍스트 매치) 비교

5-1 쿼리를 knn 대신 `text` 필드 BM25(`match`) 쿼리로 재실행. 목적: 정답
문서(R26BK01624671_000)가 BM25로는 상위에 뜨는지 확인해 하이브리드 검색
도입 근거를 만드는 것.

**결과: BM25로도 R26BK01624671_000이 top-5에 뜨지 않았고, "eLoran" 단독
검색도 인덱스 전체에서 매치 0건이었다.**

### 원인 규명

BM25가 못 찾은 게 아니라, **"eLoran"이라는 단어 자체가 인덱스에 존재하지
않았다.** 원본 문서(`R26BK01624671_000_doc01`)를 직접 확인한 결과:

- "eLoran"은 원문 1,445번째 글자 위치, `사업명: | eLoran 수신기 보정지도
  지원 시스템 구축` 표 안에 있음
- 이 표는 **7,096자짜리 초대형 [표] 블록**(청렴계약서약 등 여러 항목이
  한 표에 다 들어있음)의 일부
- 청킹 로직(기존에 merge된 표 잘림 처리: 768자 초과 시 완전 행 단위 절단)이
  이 표를 **691자만 남기고 절단** — "eLoran"이 있던 위치(1,445)는 이미
  절단선 밖이라 **살아남은 청크에 "eLoran"이라는 문자열 자체가 없음**

즉 이번 케이스는 BM25 vs knn의 성능 차이가 아니라, **표 절단 시 "앞부분만
남기는" 전략이 하필 문서를 식별하는 핵심 정보(사업명)를 잘라낸 사례**다.
청크 데이터에 없는 정보는 BM25든 knn이든 원천적으로 못 찾는다.

### 시사점

1. **하이브리드 검색(BM25+knn) 도입이 여전히 유효한 다음 개선 방향이다** —
   이번 케이스는 우연히 절단 손실과 겹쳤을 뿐, 5-1의 정상 케이스들(다른
   문서의 "입찰참가자격" 문구)에서 보듯 정확한 키워드가 살아있는 문서라면
   BM25가 knn이 놓치는 정확 매치를 보완할 여지는 여전히 있다. 다만 이번
   테스트로 그 근거를 직접 확인하지는 못했다(정답 문서 자체가 절단으로
   빠져 있었기 때문) — 청킹을 고친 뒤 재검증이 필요하다.
2. **표 절단 전략 재검토가 더 시급한 발견이다** — 현재 "앞부분만 남기고
   뒷부분을 버리는" 절단(768자 한도)이, 사업명·공고번호 같은 핵심 식별
   정보가 표 뒷부분에 있으면 그대로 날려버린다. 전체 2,624개 청크 중
   truncated 319건(약 12%)이 있어 유사 사례가 더 있을 가능성이 있다.
   개선 방향 후보(우선순위 미정, 다음 단계에서 논의):
   - 표에서 식별 정보(공고번호/사업명/수요기관 등 헤더 행)를 우선 보존하고
     나머지를 자르는 방식으로 절단 전략 변경
   - 절단되는 표 청크에 한해 원문 전체를 별도 필드(SQL 조회용)로 같이
     저장 — 현재도 원본 raw 데이터는 남아있어 접근 자체는 가능하나, 검색
     인덱스 안에서는 여전히 못 찾음

## 7. 종합

- 임베딩(Cloudflare BGE-M3) → OpenSearch knn 인덱싱 → 검색까지 파이프라인
  자체는 정상 동작 확인(2,624건 전체 성공, 무관 질문에 스코어 유의미하게
  하락)
- 다음으로 손볼 항목은 검색 알고리즘(BM25/하이브리드)보다 **청킹의 표
  절단 전략** — 이번 실험이 실제 데이터 손실 사례를 하나 구체적으로
  찾아냈다.
